# Native Product Rebuild Migration

## Canonical replacement

The prior monolithic `ContentView`, tracked-link settings, App Store Connect credential flow, Cloudflare Worker client, JWT helper, CloudKit configuration, and remote-notification/background entitlements were replaced by one local-first path.

Every production entry now resolves through `ContentView`, `MainView`, and `LibraryView`. The retired Today tab, campaign/recipient/template/distribution pages, batch-detail navigation, and their feature services were deleted rather than hidden. There is no duplicate router, permanent feature flag, or second persistence container.

## Product-aware code categories

`CodeCategory` is the canonical boundary between an App and its imported batches. It separates codes for subscriptions, free offers, percentage discounts, launch promotions, or other products even when every group contains hundreds of codes.

The additive startup migration creates categories for legacy batches and groups compatible product/offer metadata without rewriting code identities. CSV inspection and import assign every new batch to an existing or newly created category. Backup schema 2 stores category identities; schema-1 restore reconstructs categories before reconnecting batches.

Navigation no longer exposes import batches. Categories are selected from the canonical native Get Codes Alert and are browsed only from the secondary Manage Codes hierarchy. This replacement prevents App → detail → batch → code navigation from returning as a parallel daily flow.

## Retrieval-first distribution

The former App → category → raw code list and retrieval Sheet were replaced, not retained. Tapping an App now presents one native Get Codes Alert. The user enters a quantity and chooses a code type only when the App has more than one. Confirmation pushes exactly one canonical result page; there is no form page or second presentation jump.

`RedeemDeckRepository.reserveCodes` prepares the requested quantity in one SwiftData transaction and selects the earliest-expiring available codes first. An insufficient request changes nothing. The selection is represented by an immutable `PreparedCodeSelection`; SwiftData models never leave the model actor.

Copy, completed system share, and successful photo save mark only pending codes as Sent and present the shared Undo action. Undo restores only codes changed by that action to Pending. The redundant result-toolbar Share action was removed; individual-code sharing remains in Code Details. Status remains editable from the secondary code browser and detail menu.

Opening and copying redemption links as separate detail actions, delivery forms, recipients, campaigns, templates, follow-up state, and distribution-history UI were removed. Retrieval history is derived only from persisted retrieval IDs and reopens the canonical result; it is not a second delivery model.

Raw-code management is deliberately separate from retrieval. Manage Codes, the category browser, and code details do not contain a Get Codes call to action. All new retrievals begin from the App row in the library.

## Four-state lifecycle

The active lifecycle is Available → Pending → Sent, with Expired computed from the expiration date and shown in preference to the delivery state. Preparing a retrieval creates Pending inventory; a successful output action creates Sent inventory. Sent records delivery from RedeemDeck, not confirmed App Store redemption.

The former Redeemed and Revoked states are retired. Startup migration maps legacy redeemed records to Sent and legacy revoked records to Archive, then clears the old flags. Backup restore applies the same normalization. The old properties remain on the model only until a versioned SwiftData migration can remove them safely.

## Durable pending migration

Leaving a retrieval result no longer silently releases its codes. Unsent codes remain Pending, appear in Continue Retrieval on the library, and can be reopened after app relaunch. The user must explicitly confirm Return to Inventory to release them.

`OfferCode.retrievalID` owns this lifecycle. The additive startup migration assigns a unique ID to every older reserved code that has no retrieval owner, preserving that code as a resumable one-code selection instead of making it accidentally available.

Backup schema 4 stores retrieval IDs and the optional per-App poster greeting. Schema-1 through schema-3 files remain supported: missing newer fields decode as `nil`, then the normal additive migration establishes a safe retrieval owner after restore. Retrieval state, identity, and greeting round-trip in current backup tests.

Poster images are generated by an actor away from the UI actor, and batch photo save loads App artwork once per operation. The current poster is a black-and-white portrait composition with a square scan field, rounded QR modules, and rounded finder patterns. Its center always contains either real App artwork or a generated initial fallback, and Vision decoding is part of the automated verification. Result layers stay alive across segmented switching. Multiple posters use one real `ZStack` pile: only the top card accepts a drag, an incomplete drag springs home, and a committed swipe moves that card to the back while promoting the next cards. Only the top three actual posters are rendered, preventing large batches from being generated at once.

## Persisted compatibility data

Older stores and backups may contain campaigns, recipients, templates, distribution records, activities, tracked-link identifiers, URLs, timestamps, and visit counts. Their model and backup records remain solely to keep existing stores readable and backups lossless. No current UI or service interprets these records as active behavior, and the app no longer creates activity records.

Owner: the app schema, `OfferCode`, and `BackupRepository` compatibility records.

Removal gate:

1. Introduce a versioned SwiftData migration that safely removes the compatibility models and properties.
2. Increment the backup schema and migrate all supported archives.
3. Verify fixture upgrades from the upstream schema and both current backup versions.

Git history is the backup for deleted production implementations; replaced source files are not retained in production folders.

## Storage and sync

The canonical configuration is a local SwiftData store. CloudKit is intentionally absent. Cross-device transfer uses explicit complete-backup export and merge restore. Deleting the app deletes its database unless the user exported a backup.

## Product rename and backup compatibility

The independent product is named RedeemDeck. The Xcode project, targets, modules, source groups, tests, repository types, migration service, backup archive, exported filenames, notification identifiers, and user-facing copy use that name.

Pre-rename backups remain supported through one import-only Uniform Type Identifier: `app.pythonide.codevault.backup`, with the `.codevaultbackup` extension. RedeemDeck exports only `app.pythonide.redeemdeck.backup` files with the `.redeemdeckbackup` extension. The Codable payload remains schema-versioned, so renaming Swift types does not change archive keys.

Owner: `RedeemDeckBackupDocument`, `BackupCodec`, and the backup restore tests.

Removal gate: remove the upstream import type only after the documented support window no longer includes backups created before the product rename and a migration release has instructed users to re-export them.

## Security boundary

Codes are deliberately shown in full in the retrieval workflow so the product has one predictable display contract. The app does not claim an additional privacy mask, application lock, clipboard timer, or database-encryption layer. Protection comes from the iOS app sandbox and device security. Exported backup JSON contains complete codes and must be handled as sensitive data.
